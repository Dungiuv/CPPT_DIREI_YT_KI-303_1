# Обробка даних автопарку

CLI-застосунок читає поїздки автопарку з UTF-8 CSV, перетворює кожен рядок на
незмінний об'єкт одного з підтипів `Trip`, перевіряє записи та обчислює
підсумкові показники.
Некоректні рядки не впливають на статистику; у звіті вказано їхні номери й
причини відхилення. Звіт виводиться в консоль і записується у файл.

## Формат CSV і правила перевірки

Кожен непорожній рядок містить п'ять полів, розділених крапкою з комою:

```text
vehicle;driver;km;fuelLiters;date
```

- `vehicle` і `driver` мають бути непорожніми.
- `km` і `fuelLiters` мають бути скінченними невід'ємними числами.
- `date` має бути коректною датою ISO у форматі `YYYY-MM-DD`.
- Порожні рядки пропускаються. Інша неправильна кількість полів, дата або
  значення відхиляють цей запис; помилка містить номер рядка.

Перевірка полів виконується під час створення `Trip`. Статичний фабричний метод
`Trip.fromCsv` розбирає CSV-рядок і створює відповідний підтип. Якщо назва
`vehicle` містить `Truck`, `MAN`, `Volvo`, `DAF`, `Scania` або `Вантаж`
(без урахування регістру), запис вважається вантажною поїздкою; інші записи —
пасажирськими. Це правило не додає поля до CSV і не змінює його формат.

## Модель поїздок

`Trip` — абстрактний базовий клас зі спільними полями `vehicle`, `driver`,
`km`, фактичною витратою `fuelLiters` і `date`. Його конструктор одноразово
перевіряє спільні інваріанти: назва транспортного засобу й водій не порожні,
дата не `null`, а кілометраж і фактичне пальне є скінченними невід'ємними
числами. `PassengerTrip` і `CargoTrip` успадковують ці поля та правила.

`TripKind` задає фіксовані категорії `PASSENGER` і `CARGO` з українськими
підписами. Кожен підтип повертає свою категорію через перевизначений
`getKind()`, тож клієнтський код не визначає її через перевірку класу.

Абстрактний клас обрано замість інтерфейсу, оскільки всі поїздки є різновидами
однієї предметної сутності й мають спільний стан та валідацію. Відмінну
поведінку задає `calculateNormativeFuelLiters()`: для пасажирської поїздки
використовується навчальний норматив 8 л/100 км, для вантажної — 25 л/100 км.
Цей нормативний розрахунок відокремлений від фактично витраченого пального:
поточний звіт продовжує використовувати `fuelLiters` із CSV і зберігає
попередні показники та формат. Поліморфна поведінка перевіряється тестом
`mixedTripsUseOverriddenBehaviorThroughBaseType`: для двох поїздок по 100 км
в `List<Trip>` він очікує відповідно 8 л і 25 л нормативного пального через
виклик одного методу базового типу.

Контролер зберігає різнорідні записи у `List<Trip>`. `MileageFuel` зберігає
незмінні сумарні кілометри й фактично витрачене пальне.

Логічна рівність `Trip` враховує конкретний клас і значення всіх спільних
полів: `vehicle`, `driver`, `km`, `fuelLiters` і `date`. Тому два об'єкти
різних підтипів не рівні лише через однакові спільні поля. `equals` і
`hashCode` реалізовані узгоджено в базовому класі; поїздки незмінні, тож
їх можна безпечно зберігати в `HashSet`.

## Структура програми

- `Main` — мінімальна точка входу: запускає парсер параметрів, контролер і
  повідомляє про помилки аргументів.
- `ArgumentsParser` — перевіряє аргументи командного рядка та повертає опції
  запуску.
- `TripController` — координує читання файлу, обробку поїздок, створення звіту
  та його виведення.
- `Trip` — незмінний абстрактний базовий тип поїздки з приватними `final`
  полями, спільною перевіркою інваріантів, фабрикою `fromCsv`, абстрактним
  нормативним розрахунком, методами читання й `toString`.
- `PassengerTrip` і `CargoTrip` — конкретні підтипи з власною реалізацією
  `calculateNormativeFuelLiters()`.
- `MileageFuel` — record для незмінних підсумків кілометражу та пального.
- `VersionInfo` — читає версію, яку Maven підставляє у ресурс
  `version.properties` з `<version>` у `pom.xml`.

На відміну від попередньої роботи, поля CSV більше не перевіряються та не
обробляються за індексами в циклі. Кожен валідний рядок стає об'єктом `Trip`,
а показники обчислюються за списком сутностей. Формат CSV, правила відхилення,
формули показників і зовнішній звіт збережені.

## Показники

Звіт містить кількість коректних поїздок, сумарний кілометраж, середню витрату
пального на 100 км та найбільшу поїздку. Середню витрату обчислено як
`сумарне пальне / сумарний кілометраж × 100`; при нульовому кілометражі
результат дорівнює `0.00`. Якщо немає коректних записів, найбільша поїздка
дорівнює `0.00 км`.

Приклад вхідного файлу: [data/input.csv](./data/input.csv).

## Збірка і запуск

Потрібна Java 21. Maven Wrapper завантажує зафіксовану версію Maven, якщо її
ще немає в локальному середовищі.

Linux або macOS:

```bash
./mvnw test
./mvnw verify
./mvnw package
java -jar target/labs-3.0.0.jar
```

Windows:

```powershell
.\mvnw.cmd test
.\mvnw.cmd verify
.\mvnw.cmd package
java -jar target\labs-3.0.0.jar
```

Типовий вхідний файл — [data/input.csv](./data/input.csv), типовий файл звіту —
`out/report.txt`. Шляхи можна змінити:

```bash
java -jar target/labs-3.0.0.jar --input data/input.csv --output out/report.txt
```

Підтримуються `-h` / `--help`, `--version`, `-i` / `--input PATH` та
`-o` / `--output PATH`; також доступні форми `--input=PATH` і `--output=PATH`.
Версія в `--version` і назва JAR походять від Maven-версії в `pom.xml`.

## Тести, якість і CI

JUnit 5 перевіряє CLI, звіт, інваріанти `Trip`, фабрику `fromCsv`, коректні,
граничні та хибні значення, категорії enum, поліморфні розрахунки,
`equals`/`hashCode`, поведінку в `HashSet` і точний звіт для контрольного CSV.
`verify` додатково запускає SpotBugs. GitHub Actions виконує `test`, `verify`
і `package` на Ubuntu, Windows та macOS і завантажує зібрані JAR як артефакти.
Для release-тега CI перевіряє, що номер версії у тегу відповідає версії у
`pom.xml`.

Щоб згенерувати Javadoc:

```bash
./mvnw javadoc:javadoc
```

На Windows використовуйте `.\mvnw.cmd javadoc:javadoc`. HTML-документація
з'явиться у `target/reports/apidocs/index.html`.

Деталі перебудови й результати перевірок наведено у
[звіті лабораторної роботи](./REPORT.md).
